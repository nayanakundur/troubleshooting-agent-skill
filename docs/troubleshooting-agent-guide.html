Overview

What Is the Troubleshooting Agent?

The Troubleshooting Agent is an AI-powered Product Support Engineering skill that automates the full investigation lifecycle for Itential Service Desk tickets. A support engineer invokes it with a single command — /troubleshoot ISD-9261 — and it reads the ticket, cross-references known issues, authenticates to the customer environment, runs targeted platform diagnostics via specialist sub-skills, and produces structured findings ready for action. All Jira writes require explicit engineer approval before execution.

Lifecycle

3-Phase Investigation Lifecycle

Every investigation follows three structured phases, followed by four closing phases. The Investigation Protocol (8-section customer communication standard) runs continuously throughout all phases.

1
Offline Only

Ticket Understanding & Triage

Reads full ISD ticket. Extracts structured context. Checks platform support status (EOL detection). Mines ISD + ENG Jira for similar cases. Searches Confluence for runbooks. Detects priority mismatches immediately. Generates engineer question list. Produces pre-investigation summary. No platform authentication.

2
No Orchestrator Auth

Symptom Analysis & Routing

Addresses remaining Investigation Protocol gaps. Classifies issue as Functional or Performance. Routes to the correct sub-skill(s) — each sub-skill authenticates itself from .env. After diagnosis, routes to builder-skills for fix construction (Constructive Fix Path).

3
Auth Here

Reproduce & Workaround

Discovers all .env and .env.* files. If multiple exist, presents a numbered list showing each environment's PLATFORM_URL and asks engineer to choose. Authenticates with selected env. Reproduces root cause. Invokes builder-skills for workarounds in the same environment. Optionally invokes platform skills (/mongodb, /redis, /prometheus, /itential-platform, /itential-gateway) to validate the reproduction environment's component health before or after reproducing the issue. For VM / bare-metal reproduction, pulls platform RPMs from JFrog using scripts/pull-platform-rpms.sh (requires JFROG_TOKEN).

4
Deliverable

Diagnostic Report

Structured report: environment snapshot, investigation checklist, ranked root-cause hypotheses with evidence, next steps with owners, access gaps table. Saved to data/{TIMESTAMP}/diagnostic_report.md.

5
Engineering

ENG Escalation Pack

When a platform bug is confirmed. Drafts ENG bug report. Creates or updates ENG Jira ticket. Links ENG to ISD. All writes require explicit engineer approval.

6
Closeout

Resolution Learning

When fix is confirmed. Records symptom-to-fix pattern in known-resolutions.md. Posts resolution comment to ISD. Transitions ticket. Updates Phase 2 routing table.

7
Escalation

Manager Escalation

On SLA breach, priority mismatch, or S1/S2 events. Priority mismatch detection fires in Phase 1 Step 1f — at ticket intake, before any investigation. Drafts Slack escalation to senior management. Upgrades priority with approval.

Agent Design

How the Agent Works — AI Design Patterns

The Troubleshooting Agent is built on a small set of well-established agentic AI patterns. Understanding these helps explain why it behaves the way it does — why it pauses before writing, why it loads different skill files for different problems, and how it accumulates knowledge across tickets.

✳

Orchestrator + Subagent

One primary skill coordinates the investigation. It delegates targeted diagnostics to six specialist sub-skills — each owning a specific domain (adapters, databases, infra, etc.). Sub-skills run independently with their own authentication and report findings back to the orchestrator for synthesis.

Multi-agentDelegation
📄

Skill-as-Prompt

Each "agent" is a structured markdown instruction file (SKILL.md) — not compiled code. The model loads the file, follows its phase-by-phase instructions, and executes the prescribed tool calls. Behavior is changed by editing a text file, not redeploying software.

Prompt-drivenNo build step
🔄

Tool-Augmented Reasoning (ReAct)

The model alternates between reasoning and acting: it formulates a hypothesis, calls a real tool (curl, SSH, AWS CLI, Jira MCP), observes the result, updates its model of the situation, and calls the next tool. This loop continues until the skill's exit condition is met.

Reason → Act → ObserveReal tool calls
🔒

Human-in-the-Loop Gates

All destructive or write operations — Jira comments, adapter config changes, tofu apply, platform restart — require an explicit engineer "yes" before execution. The model presents the exact payload and waits. It cannot bypass a gate even in autonomous mode.

Approval requiredRead-only default
🗂

Filesystem Memory

Short-term: per-ticket markdown files (ticket_context.md, diagnostic_report.md) written under data/{TIMESTAMP}/. Long-term: append-only known-resolutions.md that grows across all investigations. No vector database or embeddings — Claude's context window does the retrieval.

Per-ticket artifactsCumulative KB
🧩

Vendor Skill Composition

Platform skills and builder skills are vendored as instruction files from private/public GitLab and GitHub repos. Local overrides (LOCAL-EXTENSIONS.md) extend vendor behavior using [OVERRIDE] and [INSERT AFTER Step N] markers — without touching the upstream source, so syncs never overwrite customizations.

Plugin patternSync-safe overrides
The Agent Harness — Claude Code
What is a harness? — An LLM can reason and produce text, but it cannot run a command, open a file, or call an API on its own. The agent harness is the runtime layer that wraps the model and gives it hands: it receives tool-call requests from the model, actually executes them (bash, file read, HTTP), and feeds the result back as the next observation in the loop. The harness also manages the context window (compacting old turns), enforces permission gates (allow/deny per tool), runs pre- and post-tool hooks, and controls the agentic loop itself (how many turns, when to stop).
Claude Code is the harness here. — When an engineer types /troubleshoot ISD-9261, Claude Code loads CLAUDE.md and the relevant SKILL.md into context, starts the agentic loop, and executes every tool call the model emits — curl, SSH, AWS CLI, Jira MCP, file reads and writes. It enforces the permission mode (auto-approve safe reads, prompt for writes), runs the Stop hook when the session ends, and compacts context when it overflows — all invisible to the model. Without the harness, the SKILL.md files are just text; with it, they become a working agent.

On-Demand Builder-Skill Invocation

The troubleshooting agent routes to a builder-skill on either trigger — no need to wait for full Phase 3 root cause confirmation.

Trigger 1 — Root cause confirmed — Phase 3 diagnosis identifies a fixable asset issue. The agent offers to construct the fix via the appropriate builder-skill and waits for engineer approval before invoking.
Trigger 2 — Direct engineer request — Engineer asks to mock, build, design, or reproduce any asset at any point in the investigation. Examples: "mock this workflow", "build a test command template", "reproduce the failing JSON form". The agent routes immediately to the right skill.
Routing by asset type — Workflows and templates → /builder-agent · JSON Forms → /itential-json-forms · MOP / command templates → /itential-mop · LCM models → /itential-lcm · IAG services → /iag · Free-form exploration → /explore · Acceptance testing / as-built → /qa-agent
Reproduce first, then apply — The agent targets the reproduction .env (Docker local) first. Once the fix is validated, it applies to the customer environment using the customer .env. All platform writes require explicit engineer approval.
Keeping skills and templates current — Run scripts/sync-builder-skills.sh to pull the latest from upstream. Review git diff vendor/builder-skills/ .claude/skills/ before committing — never auto-apply without review.
Manifest audit trail — vendor/builder-skills/SYNC_MANIFEST.json records the upstream commit SHA, branch, and sync timestamp for both helper bundles and skill files. Always matches what's vendored — no ambiguity about provenance.

Output Interpretation

Reading Your Diagnostic Report

The diagnostic report (data/{TIMESTAMP}/diagnostic_report.md) is the primary deliverable from Phase 5. Here's how to interpret each section.

Environment Snapshot

Versions and states of every component at investigation time. Cross-check IAP version against the ticket — customers sometimes report the install version, not what's actually running.

Findings

Each finding has: What (what was observed), Evidence (the specific log line, metric, or API response that confirms it), Relevance (why it matters to the symptom).

Root Cause Hypotheses

Ranked by likelihood. The top hypothesis has the most supporting evidence. Lower-ranked ones are kept if the top hypothesis doesn't hold after testing. Never skip to a fix without validating the top hypothesis.

Access Gaps

Variables missing from .env that would unlock deeper investigation. Each gap lists exactly what investigation it blocks. Add the variables and re-run to go deeper.

job.error is an array: Always iterate all entries — never just check the first. A job can accumulate multiple errors across retries and branches. status: complete doesn't mean success — always check job.error on complete jobs too.

FAQ

Frequently Asked Questions

Can the agent post comments to ISD tickets automatically? No. The agent always presents the draft comment first and waits for your explicit approval before posting anything. This applies to questionnaire posts, resolution comments, and escalation notices.
Can the agent restart services or adapters? No — not without your explicit consent in the conversation. It will always ask: "I will restart the {ADAPTER_NAME} adapter. Proceed?" You must confirm before any restart happens.
The agent says it can't investigate MongoDB — why? MONGO_URL is missing from your .env. The diagnostic report's "Access Gaps" table lists exactly which variables are missing and what each one unlocks. Add them and re-run.
Can I run sub-skills without running the full /troubleshoot? Yes. All sub-skills are independently invocable: /troubleshoot-adapters my-adapter, /troubleshoot-jobs job-id, etc. They read the same .env credentials and produce their own output files.
A job shows status:complete but the agent says to check job.error — why? status: complete means the workflow reached workflow_end. It does NOT mean no errors occurred. A workflow can route through an error handler and still complete. Always check job.error[] on complete jobs.
Why does the agent ask about adapter "type name" vs "instance name"? The app field in a workflow task must be the adapter type name from apps.json (e.g., ServiceNow). The adapter instance name (e.g., servicenow-prod) belongs in adapter_id only. Using the instance name in app causes "No config found for Adapter" at runtime — every time.
When should I invoke /troubleshoot-logs vs letting /troubleshoot do it? Run /troubleshoot-logs directly when: (1) you need to collect logs as an artifact for a customer or ENG ticket, (2) you're investigating a specific incident time without a full investigation, or (3) the primary skill already ran and you need deeper log evidence. The primary skill calls it automatically in Phase 3 when log evidence is needed to confirm a finding.
How does the agent handle IAG vs adapter OFFLINE differently? IAG OFFLINE is almost always token_timeout: -1. The agent checks this first (Phase 3d inline). Adapter OFFLINE could be network, credentials, wrong host, or stub mode — the adapter sub-skill runs a full gather → debug → cleanup cycle with your approval at each step.
How does the agent behave differently for cloud (itential-saas) customers vs on-prem? For cloud customers (project_type = itential-saas or *.itential.io URL), the agent detects the deployment at triage and stamps a cloud topology block into ticket_context.md. All sub-skills then adjust: no SSH to IAP nodes (Itential-managed), SSH to IAG on-prem hosts is still available, and adapter OFFLINE diagnostics lead with the Itential NAT IP whitelist check before credentials or settings. See the Itential Cloud Customers section for the full capability matrix.

How the Agent Learns — Knowledge Sources

The troubleshooting agent draws from six distinct knowledge layers during every investigation. Understanding what each layer covers — and how to improve it — directly improves diagnosis accuracy and speed.

LR

Local Reference Files

Two manually maintained files in data/ that grow with every investigation:

At triage Step 1d, the agent searches both ISD (past support cases) and ENG (engineering bugs) using the error string and component from the current ticket. It extracts:

  • Root-cause comments and resolution steps from resolved ISD tickets
  • Workarounds from ENG bugs whose fix version is ahead of the customer's version
  • Open ENG bugs with linked ISDs (used for Phase 5 escalation)

Saves to known_issues.md.

At triage Step 1e, three CQL queries search Confluence for pages matching the error string, component, and symptom keywords. The agent prioritizes:

  • Step-by-step runbooks (titles containing "runbook", "investigation")
  • Incident post-mortems ("root cause", "incident")
  • Version-specific release notes and known-behavior notes

Saves to confluence_references.md. Passed to sub-skills in the Phase 2 invocation.

At triage Step 1e-docs, the agent searches the public docs website in real time using WebSearch site:docs.itential.com. Routing is automatic by ticket signals:

  • Platform — always consulted (IAP behavior, API contracts)
  • IAG 4 or IAG 5 — by detected gateway version
  • Adapters — for any adapter-* package (OSS)
  • Cloud — for *.itential.io SaaS customers
  • Cisco NSO — for adapter-nso / NSO-related issues

Saves to docs_references.md. Passed to sub-skills in Phase 2.

Phase 2 sub-skills connect directly to the customer environment via the platform API and SSH. This provides ground-truth state:

  • Live adapter settings vs. expected sampleProperties
  • Failing job details, task-level error arrays, childJob chains
  • MongoDB slow query logs, COLLSCAN counts, replica set state
  • IAP + IAG + LB log excerpts correlated by timestamp
  • Container resource usage (OOMKilled events, disk saturation)

Tips to Improve Troubleshooting Capabilities

The agent is only as good as the knowledge it can access. These practices directly improve what it finds and how confidently it diagnoses.

Keep product-capability-reference.md current. Add a new row to §1b (version history) every time a new IAP release drops. Capture version-specific behavioral differences in §7 — they are stamped onto every ticket context and prevent sub-skills from testing features that don't exist yet in the customer's version. This file is the agent's offline encyclopedia.
Always append to known-resolutions.md at Phase 6. Every confirmed root cause logged here is immediately available to every future investigation. A two-line entry (symptom pattern → fix + version range) can save 30 minutes on the next ticket with the same error string. The agent prompts you to append at Phase 6 — don't skip it.
Write Confluence runbooks with searchable titles. The triage CQL queries match on page title and body text. Include the component name (Adapter, MongoDB, IAG), the symptom or error, and a keyword like "runbook", "investigation", or "root cause" in the title. A page titled "adapter-nso OFFLINE investigation runbook" will surface in every NSO adapter ticket; a page titled "NSO notes" will not.
Tag ENG bugs with accurate affectedVersions and fixVersions. The agent compares these fields against the customer's installed version to determine whether the bug is patched. A bug with no fixVersions and missing affectedVersions is effectively invisible to the triage lookup and won't surface as a known issue even when it matches.
Attach logs to ISD tickets — even partial ones. Triage Step 1a-attach parses log and error attachments to extract a precise incident timestamp, which becomes the search anchor for /troubleshoot-logs. A customer's "around 10:30am" is far less useful than the exact 2026-08-13T10:28:43Z extracted from an attached stack trace.
File IPSO tickets with complete reproduction steps. When the agent handles IPSO tickets, it reads the description and all comments to build its initial hypothesis. Sparse IPSO tickets ("adapter breaks sometimes") produce weak triage. Detailed ones ("adapter-cisco-ios fails auth after token_timeout:1800 elapses on IAP 6.3.1, works on 6.3.0") enable a confident version-range analysis and matching ENG bug draft.
Sync builder-skills before Phase 3 work. Run scripts/sync-builder-skills.sh --check to see if the vendored templates are behind upstream. Stale templates may lack newer operation signatures or JSON Forms schema patterns — the agent will warn you at Phase 3, but syncing proactively avoids the interruption.

Frequently Asked Questions — How the Agent Knows What It Knows

Does the agent look at docs.itential.com in real time, or does it use a cached snapshot? Real time. At triage Step 1e-docs, it runs WebSearch site:docs.itential.com queries against the live public website and fetches the matching pages. The results are saved into docs_references.md in the ticket folder — this is a fresh pull per investigation, not a cached copy.
How does the agent know if a feature or API exists in the customer's IAP version? Two sources work together: product-capability-reference.md §7 (version-specific behavioral notes, stamped onto every ticket context at triage) and live docs.itential.com lookups for the customer's exact IAP version. If a feature was introduced in 6.4 and the customer is on 6.2, the behavioral notes flag it as not available and sub-skills skip any diagnostic steps that depend on it.
Which knowledge source has the highest priority when there's a conflict? Live platform data wins. If the adapter settings pulled directly from the customer's environment contradict what sampleProperties or Confluence says should be there, the live data is the ground truth. The agent notes discrepancies and uses them as diagnostic evidence. docs.itential.com defines expected behavior; the platform API reveals actual behavior.
Can the agent learn from tickets it investigates, or does knowledge only come from what's already written? It learns through Phase 6 (Resolution Learning). After each confirmed resolution, the agent appends the root cause pattern, the fix, and the IAP version range to data/known-resolutions.md. That entry is immediately available to every future triage — the agent reads known-resolutions.md at Phase 1 before starting any new investigation.
Does it search Confluence automatically, or do I have to ask? Automatically, at triage Step 1e. Three CQL queries run against Confluence (error string, component runbooks, symptom + post-mortem keywords) for every ISD, IPSO, and ENG ticket. You don't have to prompt it. Results land in confluence_references.md before the agent generates the pre-investigation summary.
What docs sections does the agent consult for a Cisco NSO adapter ticket? Both the Adapters section (site:docs.itential.com/adapters) and the Cisco NSO section (site:docs.itential.com/cisco-nso), plus the Platform section (always included). If the ticket also involves IAG, the IAG4 or IAG5 section is added based on the detected gateway version.
What happens when the agent can't reach docs.itential.com or Confluence? It fails open and continues the investigation using what it has locally: product-capability-reference.md, known-resolutions.md, and any prior Jira mining results. The pre-investigation summary notes which live lookups were skipped. Platform diagnostics (Phase 2 sub-skills) are not affected — they connect directly to the customer environment, not to external documentation sites.
Cloud Customers

Itential Cloud Customers (itential-saas) — Topology & Diagnostics

When project_type = itential-saas or the platform URL is *.itential.io, the agent automatically detects a cloud deployment and adjusts every diagnostic step. Understanding this topology prevents misguided troubleshooting steps.

☁

IAP — Itential-Managed Cloud

IAP runs on Itential's cloud infrastructure. Support engineers cannot SSH to IAP application nodes. All IAP diagnostics use the platform API (*.itential.io). Container logs from IAP nodes must be requested from Itential cloud ops.

IG

IAG — Customer On-Premises

IAG4 or IAG5 is installed and managed by the customer on their own premises. SSH to IAG hosts is available via SSH_HOST_N entries in .env (use SSH_ROLE=gateway). IAG connects outbound to cloud IAP.

NA

Adapters — Itential NAT Layer

All adapter and integration traffic from cloud IAP is routed through Itential's NAT layer. The target system (ServiceNow, NetBox, Cisco NSO, IPAM, ITSM, etc.) sees Itential's NAT IP — not the customer's on-prem IP. The target must whitelist the Itential NAT IP.

Adapter OFFLINE on Cloud — Diagnostic Priority

1. Confirm the current Itential NAT IP with cloud ops — before any other adapter diagnostic step for a cloud customer. The target system sees only this IP; the customer's on-prem IP is irrelevant.
2. Verify the NAT IP is in the target system's allowlist — ask the customer to check firewall/IP allowlist rules on ServiceNow, NetBox, or whichever system the adapter connects to.
3. NAT IP rotation is the most common cause of sudden OFFLINE — if the adapter was working and went OFFLINE with no customer-side change, a NAT IP change from a cloud infrastructure event is the most likely cause. Check this before settings or credentials.
4. Never ask the customer to whitelist their own on-prem IP — adapter traffic leaves from Itential's cloud, never from the customer's on-prem network.

Outage Reports

Outage Summary Report & Problem Ticket Clone

When a ticket is classified as a production outage, Phase 4 branches into an additional flow that produces a six-section outage_summary_report.md and offers to create a linked Problem ticket for RCA tracking — so the customer ticket and the root-cause investigation can be managed independently.

OT

Auto-Detection

Triage Step 1f detects outage signals: bulk job failures (≥10 stuck), Jira issuetype = Incident/Problem, "platform is down", "IAG down", "adapter went OFFLINE". Sets outage_flag: true in ticket_context.md.

IN

Input Gathering

Phase 4 pre-fills from the ticket and investigation findings. For missing fields, it asks the engineer. Call transcripts can be pasted in — the agent extracts timeline, recovery actions, and next steps automatically.

AP

Approval Gates

Report draft is reviewed before saving. Posting to ISD and creating the Problem clone each require a separate explicit approval — same gate as all Jira writes. Engineer can approve or skip each step independently.

PR

Problem Ticket Clone (RCA)

After the outage report, the agent offers to create a Problem ticket pre-filled from the outage context (summary, symptoms, next steps). It links the Problem to the outage ticket and posts a cross-reference comment. Saves problem_ticket_key to ticket_context.md.

Outage Report Sections

Overview
2–3 sentence summary: what failed, when it started, scope of impact, and how long it lasted before recovery. Written for a technical manager audience — precise but not jargon-heavy.
Issue
Bulleted list of observed symptoms with scope (number of jobs, which components), what was working normally, and secondary system effects that confirmed the blast radius.
Root Cause Symptom
Plain-English description of what the evidence points to — component, communication path, and why the symptoms are consistent with that cause. Clearly distinguishes confirmed root cause from working hypothesis.
Outage Recovery
Who performed the recovery action, what was done, and at what time (with timezone). Followed by a post-recovery validation checklist — smoke test workflows run and confirmation timestamp.
Next Steps
Numbered action items with owner and target date. Always includes a Root Cause Analysis item pointing to the Problem ticket created in Step 4-OR-6 (or a placeholder if the engineer declined).
Current Status
One paragraph: immediate resolution state (resolved / monitoring / partial), what was restored, how it was confirmed, and what remains open (e.g. root cause investigation in progress via Problem ticket).

Ticket Management

Ticket Type Conversions

The agent detects when a ticket's type doesn't match what was filed and offers to convert it — with explicit engineer approval — so the right teams track and prioritize the work. All Jira type changes require a clear 'yes' before execution and include an internal comment explaining the conversion.

SR

Service Request → Enhancement Request

Detected in triage (Step 1f-SR) when issuetype = Service Request. Offered immediately after triage. Converts via editJiraIssue so product management can track and prioritize it on the roadmap.

FR

Any Type → New Feature

Detected during Phase 2 investigation when root cause analysis reveals the customer is requesting new platform behavior — not reporting a bug or misconfiguration. Offered before routing to diagnostic sub-skills.

RCA

Outage → Problem Clone

After producing the outage summary report (Phase 4-OR-6), a new Problem ticket is created — pre-filled from the outage context — and linked to the original outage ticket. Separate from the outage ISD ticket so RCA can be tracked to completion independently.

When offered
Service Request → ER: immediately after triage. Feature request: at Phase 2 before sub-skill routing. Problem clone: after outage report is saved (Step 4-OR-6). Each offer is independent — declining one does not affect the others.
Approval gate
All type changes and ticket creations require an explicit yes from the engineer. The agent presents the exact Jira fields before calling editJiraIssue or createJiraIssue. Declining does not block the investigation.
Audit trail
Every type conversion adds an internal Jira comment (Service Desk Team visibility) explaining what changed, why, and who triggered it. Problem ticket key is saved to ticket_context.md for reference throughout the investigation.
Feature request close path
If a ticket is confirmed as a feature request and the engineer chooses convert, the investigation closes gracefully — no diagnostic sub-skills are invoked for a feature gap. The engineer can also choose keep to continue investigating while noting the feature signal in the diagnostic report.

Vendor Skill Extension Policy

Never modify any file listed in vendor/platform-skills/SYNC_MANIFEST.json or any file under vendor/builder-skills/. A future sync run silently overwrites those files — local changes are lost without warning.

To add or override behavior in a vendor skill, create a LOCAL-EXTENSIONS.md file adjacent to the vendor SKILL.md. This file is NOT in SYNC_MANIFEST.json — it survives every sync unchanged.

Step 1 — Create LOCAL-EXTENSIONS.md at .claude/skills/<skill-name>/LOCAL-EXTENSIONS.md. Confirm it's not vendored: grep "<skill-name>/LOCAL-EXTENSIONS" vendor/platform-skills/SYNC_MANIFEST.json must return empty.
Step 2 — Use two section labels: [OVERRIDE] Section Name replaces the vendor instruction entirely. [INSERT AFTER Step N] adds a step at the named position; surrounding vendor steps run unchanged.
Step 3 — Add a CLAUDE.md pointer in the platform-skills section of CLAUDE.md so Claude always reads the extension file alongside the vendor SKILL.md. See the /themis-aws-deploy entry in CLAUDE.md as the template.
Canonical example: .claude/skills/themis-aws-deploy/LOCAL-EXTENSIONS.md — the reference implementation for all future vendor skill extensions.

Post-Sync Validation — Keeping Extensions in Sync

Every scripts/sync-platform-skills.sh run automatically validates any LOCAL-EXTENSIONS.md files for changed skills. Three issue types are detected:

🔴 CRITICAL (exit 2) — An [OVERRIDE] or [INSERT AFTER] anchor no longer exists in the updated vendor SKILL.md. The extension section is silently inert until repaired. Run /sync-vendor-skills to find the renamed step and update the label.
🟠 MODIFIED (exit 1) — Vendor step content changed (SHA1 hash diff against git show HEAD:{path}). Override may miss vendor improvements. /sync-vendor-skills shows a unified diff and offers keep / merge / skip.
🟡 NEW (exit 1) — Vendor added a new step not covered by any extension. Vendor step runs as-is — review whether local customization is needed. /sync-vendor-skills shows the full step and offers skip / override / insert.
Validator script: scripts/validate-extensions.py [--skill <name>] [--json] [--save]. Report saved to .claude/skills/<name>/sync-validation-latest.md with --save. Run /sync-vendor-skills --report-only in Claude Code to regenerate reports without applying fixes.

Sentinel certify reports stay remote — the Sentinel certify report is never fetched to the local reports directory automatically. The skill fetches it via scp from each sentinel host after certify_redis runs, into environments/<arch>/reports/sentinel/.

Debug Procedures

Adapter Debug Mode — Step-by-Step

The adapter debug cycle is a three-phase procedure: Gather (read-only), Debug (requires consent at each step), and Cleanup (mandatory). Never leave auth_logging: true in production.

1
Always first

Gather Phase

GET adapter settings. Compare against sampleProperties. Run critical checks: stub mode, auth_method, host/port, token_timeout, AWS key prefix. If root cause is clear from gather — fix it here, skip debug mode.

2
Only if needed

Debug Mode

Start log watcher FIRST (before any restart). Enable auth_logging: true + console_level: debug. Restart adapter (consent required). Analyze captured logs. Never skip the log watcher start.

3
Always mandatory

Cleanup Phase

Reset auth_logging: false + console_level: error. Restart adapter (consent required). Verify adapter state. Leaving debug settings exposes credentials and causes disk pressure.

Critical order: Start the log watcher BEFORE enabling debug settings. The most diagnostic logs appear immediately after the adapter restart — if the watcher isn't running yet, you'll miss the key auth exchange lines.

■ /troubleshoot-jobs — Stuck & Slow Jobs

Two investigation paths chosen at the start based on the symptom: performance regression (slow) or execution failure (stuck/errored). Path A profiles task-level timing; Path B walks the parent–child job chain.

SL

Path A — Slow Jobs

Profiles each task's duration. Pulls 5–10 prior healthy runs of the same workflow from MongoDB for baseline. Diffs task timings to isolate which task regressed. Checks concurrent job load to distinguish resource contention from a single-task regression.

ST

Path B — Stuck / Errored

Confirms true stall (task start_time vs. now — >10 min with no progress). Walks parent → child → grandchild chain for error arrays. Checks adapter and application health. Cross-correlates IAP/IAG/MongoDB/Redis logs in the incident window.

Slow baseline
MongoDB query: find prior runs of the same workflow, extract per-task timing. Build a timing baseline table (median duration per task across healthy runs). Diff the slow run against the baseline row-by-row to find the regressed task.
Contention check
Count concurrent jobs/tasks running during the slow run's time window. If contention was high on the day of the slow run but not the baseline, root cause is resource exhaustion rather than a single-task regression.
True-stall test
A task marked "running" is not necessarily stuck. Compare task.start_time to now — if >10 min with no output updates, it is a true stall. Adapter or application down at the same time is the usual cause.
Chain traversal
Walk all parent → child → grandchild job IDs recursively. Each level's job.error[] array is inspected. Origin error is at the deepest level that shows an error where the parent level shows none.

■ /troubleshoot-databases — MongoDB & Redis

Read-only diagnostics for the data layer. MongoDB path covers connection saturation, replica set health, slow queries, and missing indexes. Redis path covers memory pressure, eviction policy, and Bull queue depth.

MG

MongoDB

Ping → server status (connections, opcounters) → replica set lag → currentOp slow queries (>2s) → collection sizes → slow query log → COLLSCAN / index analysis.

RD

Redis

INFO all: memory, eviction policy, hit/miss ratio → Bull queue depths → blocked clients. Flags allkeys-lru eviction as dangerous for IAP (can silently evict job state).

EC

ElastiCache

CloudWatch metrics for managed Redis: DatabaseMemoryUsagePercentage, CurrConnections, Evictions, CacheHits/CacheMisses.

Connection saturation
Check connections.current vs. connections.available in serverStatus. If available is <10% of current, IAP will start seeing connection refusals — connection pool or MongoDB maxIncomingConnections needs adjustment.
Replica set lag
rs.status() — check each secondary member's optimeDate lag vs. primary. Lag >10s means reads from secondaries return stale data. IAP workflows reading from a lagged secondary can see "not found" for recently written jobs.
COLLSCAN detection
db.currentOp() filtered for secs_running > 2. If planSummary shows COLLSCAN, the query is doing a full collection scan — the index for that query pattern is missing.
Bull queue depth
Check queue depths for all IAP Bull queues (KEYS bull:*:waiting). A backed-up queue means jobs can't get WFE workers. Root cause is usually insufficient WFE replicas or a blocked worker consuming no items.
Redis eviction risk
maxmemory-policy: allkeys-lru is dangerous for IAP — Redis can silently evict job state keys under memory pressure. Policy should be noeviction or volatile-lru (only evicts keys with TTL set).

■ /troubleshoot-infra — CPU / Memory / Disk / Containers / EKS

Infrastructure diagnostics across all deployment types: Docker Compose, SSH/VM, and Kubernetes/EKS. Identifies OOMKilled containers, disk exhaustion, file descriptor limits, and network connectivity breaks between components.

DC

Docker / Container

docker ps -a for restarts + OOMKilled + non-zero exit codes. docker stats for live CPU% and memory usage/limit. Disk: docker system df + log directory sizes.

VM

SSH / VM

Parallel SSH collection across all SSH_ROLE_N=iap hosts. CPU load average, top processes, swap usage, /proc/{PID}/limits for file descriptor ceiling.

EK

Kubernetes / EKS

kubectl top nodes / kubectl top pods, node pressure conditions, pod OOMKilled history, PVC usage. Flags node DiskPressure and MemoryPressure immediately.

OOMKill detection
Docker: docker inspect {container} | jq '.[].State.OOMKilled'. K8s: kubectl describe pod shows OOMKilled in the last state. IAP or MongoDB getting OOMKilled is the most common cause of intermittent job failures.
Disk threshold
df -h — disk >85% on root or MongoDB data directory is flagged critical. IAP log directories fill fast under high job volume. find /var/log/itential -name "*.log" -size +500M identifies candidates for rotation.
File descriptors
FD exhaustion causes MongoDB connection failures silently (IAP sees "connection refused" with no memory pressure). Check cat /proc/{pid}/limits for the hard FD limit and ls /proc/{pid}/fd | wc -l for current count.
Network connectivity
Tests: IAP → MongoDB (nc -zv {MONGO_HOST} 27017), IAP → Redis (nc -zv {REDIS_HOST} 6379), IAP → IAG health endpoint. Firewall rule changes in the 48h before the incident are the most common cause of sudden connectivity breaks.

■ /troubleshoot-logs — Log Collection & Cross-Component Correlation

Pure collection and analysis — no platform API writes. Discovers log paths, collects from the deployment's log surfaces (Docker exec, SSH parallel, kubectl/stern, CloudWatch), filters to the incident window, and correlates timestamps across IAP, IAG, MongoDB, and Redis to find the origin failure.

CO

Collect

Discovers log paths from IAP application properties API. Collects by deployment: Docker exec, SSH parallel across all SSH_ROLE_N=iap hosts, kubectl logs/stern, or CloudWatch Logs.

FI

Filter

Greps to the incident date/window. Filters for error/warn/exception/FATAL lines. Masks sensitive values: tokens and passwords shown as first 6 + last 4 characters only.

CR

Correlate

Aligns IAP + IAG + MongoDB + Redis log lines by UTC timestamp. Produces a cross-component event timeline to find the exact sequence — e.g., Redis timeout at T+0 → Bull queue error T+2 → job stuck T+5.

Phase 1
Triage: identify which components are involved, establish the incident time window (UTC), and confirm the deployment type (Docker / K8s / VM / SaaS).
Phase 2 — IAP
Collect IAP application logs. Docker: docker exec {iap} cat /var/log/itential/app.log. SSH: parallel collection across all IAP hosts. K8s: kubectl logs {pod} --since=2h or stern {pod-selector}. CloudWatch: query log group by incident window.
Phase 3–5
Repeat collection for IAG, MongoDB (mongod.log), and Redis (redis.log / CloudWatch). Each component's logs are saved separately to data/{TIMESTAMP}/{ISD}/logs/.
Phase 6 — LB logs
Load balancer access logs (ALB / nginx): look for 502/504 errors, connection timeouts, and upstream response times in the incident window. Confirms whether failures started at the edge (LB → IAP) or deeper (IAP → backend).
Phase 7 — Correlation
Sort all log lines across components by UTC timestamp. Identify the first error in the merged timeline — that component is the origin. All subsequent errors in other components are downstream effects. Produces a correlation report attached to the Jira ticket.
Sensitive data masking
All log output shown to the engineer has tokens and passwords masked: first 6 characters + "..." + last 4. Full values are never echoed in session output. This applies even when the log file itself contains the full value.

■ /sync-vendor-skills — Post-Sync Extension Repair

Run after scripts/sync-platform-skills.sh when the post-sync validator (scripts/validate-extensions.py) detects issues with LOCAL-EXTENSIONS.md files. Reads the validation report, diffs old vs. new vendor step content, drafts specific label fixes and content merges, and applies them with engineer approval — so extensions stay aligned with updated vendor skills without being rewritten from scratch.

CR

🔴 CRITICAL — Broken Anchor

An [OVERRIDE] or [INSERT AFTER] label targets a step that was renamed or removed in the updated vendor SKILL.md. The extension section has no effect until repaired. The skill finds the closest renamed step and proposes a label update.

MD

🟠 MODIFIED — Stale Override

Vendor step content changed between old and new sync (detected by SHA1 content hash diff). The override still applies (anchor exists) but may miss vendor improvements. Shows a unified diff; engineer chooses keep / merge / skip.

NW

🟡 NEW — Uncovered Step

Vendor added a new step with no LOCAL-EXTENSIONS.md coverage. Not necessarily a problem — vendor step runs as-is unless local customization is needed. Shows full step content; engineer chooses skip / override / insert-before / insert-after.

When it runs
scripts/sync-platform-skills.sh automatically calls scripts/validate-extensions.py after each sync for any changed skill that has a LOCAL-EXTENSIONS.md. Prints ✅ / ⚠️ / 🔴 per skill. If issues are found, it prompts: "Run '/sync-vendor-skills' in Claude Code to repair them."
How to invoke
/sync-vendor-skills — review all skills with validation reports. /sync-vendor-skills themis-aws-deploy — review one skill only. /sync-vendor-skills --report-only — regenerate and print the report without applying any fixes.
Validator mechanics
scripts/validate-extensions.py uses git show HEAD:.claude/skills/{name}/SKILL.md to get the pre-sync version for comparison. Detects anchor existence (CRITICAL), SHA1 content hash changes (MODIFIED), and new steps absent from the old version (NEW). Exit codes: 0 = clean, 1 = warnings, 2 = critical.
Approval gates
Every fix is presented as a diff of LOCAL-EXTENSIONS.md before writing. For CRITICAL: shows old label → proposed new label. For MODIFIED: shows vendor diff + engineer's current override + draft merged content. For NEW: shows full new vendor step + draft extension section. Nothing is written without explicit engineer "yes".
After applying fixes
Re-runs the validator to confirm clean. Stages LOCAL-EXTENSIONS.md with git add. Prints a recommended commit message. Does NOT auto-commit — engineer commits together with the vendor SKILL.md changes.
Safety rule
Only modifies LOCAL-EXTENSIONS.md files — never the vendor SKILL.md itself. Never removes existing extension sections without explicit engineer confirmation — they may contain site-specific overrides that are still correct even if the validator flagged them.

Automated Contribution

/contribute — One Command, Full PR

The /contribute sub-skill automates the entire knowledge-loop contribution flow. It reads your closed investigation artifacts, generates properly formatted entries, presents them for your approval, and opens a GitHub PR — without you touching git.

IS

/contribute ISD-XXXX

Reads diagnostic_report.md from that ticket's investigation folder, generates a resolution entry (symptom, root cause, detection hints, workaround, verification), and appends to known-resolutions.md. Duplicate-checks before appending.

SC

/contribute scan

Scans all investigation folders in data/, lists which have diagnostic reports, and lets you select tickets to batch-contribute in a single PR. Best for end-of-sprint bulk contribution.

VN

/contribute version-note

Prompts for version range, component, and behavioral fact, then appends a §7 row to product-capability-reference.md. Cite the ISD ticket that surfaced the fact for traceability.

SF

/contribute skill-fix {name}

Describe the improvement to a sub-skill (e.g. "troubleshoot-adapters"). The agent drafts the change, presents the diff, and opens a PR targeting the skill file. Good for gotchas discovered during a case.

KB

/contribute known-bug ENG-XXXX

Fetches the ENG ticket, formats a §5 known-bug row (affected versions, fix version, workaround), and appends to product-capability-reference.md. Makes the bug visible to all future triage investigations.

ENG

/contribute ENG-XXXX

Same as known-bug shorthand — fetches the ENG ticket and appends it to the known-bug catalog. Use after confirming a bug is confirmed and has a fix version or workaround documented.

What the skill does — step by step

Preflight
Checks git status for uncommitted changes, confirms gh CLI is authenticated, and identifies the contributing engineer from git config. Warns if working tree has unsaved changes that might be at risk.
Generate
Reads diagnostic_report.md, ticket_context.md, and pre-investigation-summary.md from the ticket's investigation folder. Generates the fully formatted resolution entry with all required sections. Checks for existing duplicate entry before proceeding.
Preview & approve
Presents the full proposed content for engineer review. You can approve, edit inline, skip the ticket, or abort the session. Nothing is written to disk until you explicitly approve.
Branch & write
Pulls latest main, creates a contrib/{your-name}-{date} branch, and appends the approved content to the target file. Multiple contributions in one session share a single branch and PR.
Diff & final approval
Shows the exact git diff --staged output before committing. If the staged diff includes any file other than the two shared knowledge files (or an approved skill file), the session aborts automatically.
PR creation
Commits with a structured message listing every ticket contributed, pushes the branch, and runs gh pr create with a pre-filled PR body including ticket references and a reviewer checklist. Prints the PR URL when done.
Customer data never leaves the investigation folder. The skill stages only data/known-resolutions.md and data/product-capability-reference.md (shared knowledge files). Investigation folders (data/{timestamp}/) are gitignored and never staged or committed.
Use /contribute scan at end of sprint. The scan mode lists all investigation folders with completed diagnostic reports and lets you select which to batch-contribute. One PR per sprint is cleaner than one per ticket and easier to review.
Contribution

Contributing Back — PR-Based Knowledge Loop

Every investigation you close is a learning opportunity for the entire team. At the end of a cadence — weekly, bi-weekly, or per sprint — open a single PR that captures two types of knowledge: ISD resolution patterns and product behavioral facts. This keeps the shared knowledge base current without requiring any extra work during the investigation itself.

R

ISD Resolution Patterns

Symptom → root cause → fix rows from closed tickets. Goes into data/known-resolutions.md. Used by Phase 1 to instantly recognize repeat issues.

P

Product Behavioral Facts

Version-specific facts discovered during investigation (file paths, config keys, API differences by version). Goes into Section 7 of data/product-capability-reference.md. Used by Phase 1 to avoid wrong diagnostic steps.

Step-by-Step: Manual PR (reference — use /contribute instead)

#ActionDetail
1 Pull latest main Always start from the most recent shared knowledge base so your additions don't conflict with teammates' entries.
git checkout main && git pull origin main
2 Create a contribution branch Name it with your initials and the date so PRs from multiple engineers don't collide.
git checkout -b contrib/<initials>-<YYYY-MM-DD>
Example: contrib/mr-2026-08-20
3 Review your closed ISDs Look through data/ for investigation folders from your cadence window. Open each diagnostic_report.md — that is your source of truth for what the root cause and fix were.
4 Append to known-resolutions.md For each closed ISD that had a confirmed root cause, add one row to the table in data/known-resolutions.md:

| ISD-XXXX | <symptom keywords> | <root cause — 1 sentence> | <fix — action taken> | <IAP version> | <builder-skill or manual> |

Skip tickets that were handed off, duplicates, or where root cause was never confirmed. Quality over quantity — one accurate row beats three vague ones.
5 Append to Section 7 of product-capability-reference.md For any product behavioral fact you discovered — a file that doesn't exist in a certain version, an API endpoint that changed, a config key that moved — add a row to the Section 7 table:

| <version range> | <component> | <what applies> | <what does NOT apply / exist> | <diagnostic impact> |

Only add facts you verified directly, not things you suspect. Include the ISD ticket number in the Diagnostic Impact column for traceability.
6 Stage only the two data files Never stage .env, .auth.json, or any data/<timestamp>/ investigation folders — those are gitignored for good reason. Stage only the shared knowledge files:
git add data/known-resolutions.md
git add data/product-capability-reference.md
7 Commit with a structured message Use a consistent format so the team can scan git log to understand what was added:

git commit -m "contrib: add resolutions for ISD-1234, ISD-1235; add 23.2 config fact"

List ticket numbers for resolutions. Mention version if a Section 7 fact was added.
8 Push and open a PR git push -u origin contrib/<initials>-<YYYY-MM-DD>

Open a PR against main. PR title: [Contrib] <date> — <N> resolutions, <M> product facts. Add any context in the PR description that would help reviewers understand edge cases or unusual findings.
9 PR review & merge One peer review is enough — the reviewer checks that resolution rows have a confirmed root cause and Section 7 facts cite a ticket or direct verification. Merge with Squash and merge to keep the main branch log clean.
10 Everyone pulls after merge At the start of the next investigation session, pull main before running /troubleshoot. This ensures Phase 1 is working from the full team's accumulated knowledge, not just your own.

What Makes a Good Resolution Row

✓

Do include

Exact error text or symptom keywords the agent can pattern-match · Confirmed root cause (not a hypothesis) · Specific fix action — command run, setting changed, or Jira ENG filed · IAP version range where the issue was seen

✗

Do not include

Customer names or environment-specific hostnames · Tickets where root cause was never confirmed · Vague fixes like "restarted the service" without a reason · Credentials, tokens, or internal URLs

Rotate the PR reviewer — designate a different team member each cycle to review contribution PRs. Reviewing a colleague's resolution rows is one of the best ways to learn from their investigations without sitting in on every ticket.
