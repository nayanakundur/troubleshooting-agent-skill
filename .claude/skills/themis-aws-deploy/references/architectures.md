# Architectures Reference

## Design Summary

VM counts and host groups below are verified directly against `themis/scripts/generate_inventory.py` and `themis/vms/aws/tfvars/*.tfvars` (2026-08-12) — not the design intent, the actual code. **None of the 4 designs provision a gateway VM or create a `gateway` inventory group** — `generate_inventory.py` has zero gateway handling anywhere in the file. See "Gateway gap" below for how this skill works around it.

| Design | VMs (tfvars, no gateway) | VMs (with gateway fix) | Use Case |
|--------|---------------------------|-------------------------|----------|
| `aio` | 1 | 1 (colocated, no extra VM needed) | POC / dev / testing |
| `minimal` | 3 | 4 | Small deployments |
| `ha2` | 8 | 9 | Production HA |
| `asa` | 16 | 18 | Active-Standby dual-site |

---

## AIO (All-In-One)

Single host running everything.

**Instance name:** `all`

**Host groups generated by `gen_aio()`:**
```
redis_master     → all (same host)
mongodb_primary  → all (same host)
platform         → all (same host)
```

**tfvars (`tfvars/aio.tfvars`):**
```hcl
design = "aio"
instances = [
  { name = "all", instance_type = "t3.medium" }
]
```

**Gateway:** no dedicated VM needed or provisioned — reuse the single `all` host for the `gateway` group (see "Gateway gap" below).

---

## Minimal

3 hosts (not 4 — no gateway VM in tfvars), one role each, no redundancy.

**Instance names:** `redis`, `mongo`, `platform`

**Host groups generated by `gen_minimal()`:**
```
redis_master     → redis
mongodb_primary  → mongo
platform         → platform (vars: platform_encryption_key, platform_mongo_url, platform_redis_host)
```

**tfvars (`tfvars/minimal.tfvars`):**
```hcl
design = "minimal"
instances = [
  { name = "redis",    instance_type = "t3.medium" },
  { name = "mongo",    instance_type = "t3.medium" },
  { name = "platform", instance_type = "t3.large"  }
]
```

**Gateway:** needs a 4th VM, added via a tfvars override (see "Gateway gap" below).

---

## HA2 (High Availability)

8 hosts (not 9 — no gateway VM in tfvars) with Redis Sentinel, MongoDB replica set, dual Platform nodes.

**Instance names:**
- Redis: `redis01`, `redis02`, `redis03`
- Mongo: `mongo01`, `mongo02`, `mongo03`
- Platform: `platform01`, `platform02`

**Host groups generated by `gen_ha2()`:**
```
redis_master     → redis01
redis_replica    → redis02, redis03
redis_sentinel   → redis01, redis02, redis03
mongodb_primary  → mongo01
mongodb_replica  → mongo02, mongo03
platform         → platform01, platform02 (vars: platform_encryption_key, platform_mongo_url, platform_redis_sentinels)
```

Note: `mongodb` is one primary + two replicas via `mongodb_primary`/`mongodb_replica` — there is no single flat `mongodb` group for this design.

**tfvars (`tfvars/ha2.tfvars`):** 8 instances, no `gateway`.

**Gateway:** needs a 9th VM, added via a tfvars override (see "Gateway gap" below).

---

## ASA (Active-Standby)

16 hosts (not 17 — no gateway VMs in tfvars) across two active sites plus a tie-breaker site. **Naming is entirely `dc1-`/`dc2-`/`dc3-`-prefixed** — not the `redis01-06`/`platform01-04` style used elsewhere in this doc's history.

**Instance names:**
- DC1 (primary site): `dc1-platform01`, `dc1-platform02`, `dc1-redis01`, `dc1-redis02`, `dc1-sentinel`, `dc1-mongo01`, `dc1-mongo02`
- DC2 (secondary site): `dc2-platform01`, `dc2-platform02`, `dc2-redis01`, `dc2-redis02`, `dc2-sentinel`, `dc2-mongo01`, `dc2-mongo02`
- DC3 (tie-breaker): `dc3-sentinel`, `dc3-arbiter`

**Host groups generated by `gen_asa()`:**
```
redis_master        → dc1-redis01
redis_replica        → dc1-redis02, dc2-redis01, dc2-redis02
redis_sentinel       → dc1-sentinel, dc2-sentinel, dc3-sentinel
mongodb_primary      → dc1-mongo01
mongodb_replica      → dc1-mongo02, dc2-mongo01, dc2-mongo02
mongodb_arbiter      → dc3-arbiter
platform             → dc1-platform01, dc1-platform02 (vars: platform_encryption_key, platform_mongo_url, platform_redis_sentinels)
platform_secondary   → dc2-platform01, dc2-platform02 (same vars, separate encryption_key)
```

**tfvars (`tfvars/asa.tfvars`):** 16 instances, no `gateway`.

**Gateway:** needs 2 VMs (one per active site), added via a tfvars override — both land in a single flat `gateway` inventory group, not split into primary/secondary, since Gateway isn't paired 1:1 with a specific Platform instance in `itential.deployer`'s model (see "Gateway gap" below).

## Gateway gap

`generate_inventory.py` never creates a `gateway` group for any of the 4 designs — confirmed by grepping the file for "gateway" (zero matches in any `gen_*()` function). This skill works around it:

- **aio:** manually add a `gateway` group to the generated `inventory/hosts` pointing at the single existing host — no extra VM.
- **minimal/ha2:** provision one extra VM via a tfvars override loaded *after* the design's own tfvars (e.g. `<SKILL_DIR>/tfvars-overrides/ha2-with-gateway.tfvars`, redefining `instances` with the design's normal set plus one `{ name = "gateway", instance_type = "t3.medium" }`), then add the `gateway` group manually pointing at it.
- **asa:** same pattern, but 2 gateway VMs (`dc1-gateway`, `dc2-gateway`), both in one flat `gateway` group.
- In every case, also create an empty `inventory/group_vars/gateway/` directory so the skill's TLS-wiring and run-vars-application steps (which already handle a `gateway` case) pick it up automatically.

`scripts/fix_gateway_group.py` in this skill automates this: reads tofu's `hostnames`/`public_ips` output, adds any instance whose name contains "gateway" to a flat `gateway` group, and falls back to reusing the single aio host if none exist.

## Architecture Auto-Detection

`generate_inventory.py` detects the design from instance names in Terraform state — no manual input needed. Detection order: ASA → HA2 → Minimal → AIO.
